## Page Layout Pattern

Phase 2 uses a **list-page → detail-page** navigation pattern (not a split panel), consistent with desktop workflows where staff navigate frequently between items.

**Pattern:** Full list on `/factions`, `/nodes`, `/wars`, `/diplomacy`. Clicking a row navigates to `/factions/[id]`, `/nodes/[id]`, etc. The detail page has a "Back to [section]" breadcrumb link at top-left. Modals are used for create/edit forms only — not for detail views.

**Rationale:** Nodes and factions have enough fields (ownership history, member roster, node log) that a split panel would be cramped at 1024px minimum width. Full-page detail views allow proper timeline rendering and history sections.

**Exception — SP Catalogue:** The SP Catalogue is read-only reference data. It uses an inline search + table on a single page with no detail view. No navigation away from the page.

**Exception — Server Log:** Single page with inline filter bar. No detail view — log entries are not individually addressable.

## Component Patterns (Inherited + New)

All Phase 1 patterns (sidebar, topbar, cards, tables, badges, buttons, form fields, modals, alert banners, scrollbar, empty states) are inherited unchanged. See 01-UI-SPEC.md "Surfaces and Component Patterns" section.

### New: List Page Layout

Each list page (Factions, Nodes, Wars, Diplomacy) follows this structure:

```
[Page heading 22px/600]         [Primary action button — gold variant]
[Sub-heading 14px/400/muted]
[Filter/search bar — full width, bg-card, border-border, py-3 px-4, gap-3]
[Table — full width, inside bg-card card with border]
```

Filter bar elements:
- Search input (flex-1): placeholder text specific to page, bg-muted, border-border, 14px/400
- Type/category filter dropdowns (fixed width 160px each): shadcn Select component
- Filter bar has no "Apply" button — filters are reactive (debounced 300ms for text search, immediate for selects)

### New: Detail Page Layout

```
[← Back to [Section] link — 14px/400/muted, mb-4]
[Detail header card — faction color stripe or tier badge on left edge]
  [Item name — 22px/600/text-primary]
  [Sub-metadata row — type badge + key facts + action buttons (Edit, Delete)]
[Content sections — stacked cards, full width]
```

Detail header card: has a 4px left border using the faction's color (or `#8b7d65` for Neutral Territory / nodes with no faction color). This is the faction color stripe pattern.

### New: Ownership Timeline

Used on Node detail page. Vertical timeline, newest entry at top.

```
[OWNERSHIP HISTORY — section label 11px/600/gold/uppercase]
[bg-card card, padding 16px]
  For each ownership record (newest first):
    [dot 8px, colored by method: peaceful=#90cc90, violent=#e07840, system=#8b7d65]
    [connector line: 2px solid #3d3426, full height between dots]
    [Faction name — 14px/600/text-primary]
    [Method badge — "Peaceful Transfer" or "Violent Conquest" or "System"]
    [Date — 11px/400/text-muted, formatted "DD MMM YYYY HH:mm"]
    [Staff note if present — 14px/400/text-muted, italic]
  Current owner row has dot colored #c4a45a (gold) and "CURRENT" label in 11px/600/gold
```

Empty state: "No ownership history recorded. Assign an owner to begin the timeline."

### New: Instability Dot Indicator

Used on node list rows and dashboard (METRICS-03).

8px diameter circle (`w-2 h-2 rounded-full shrink-0`), inline-flex with level label. Color from instability color system table above.

```
[dot] [Level label — 14px/400/text-primary]
```

On the node list table: dot appears in the Instability column before the level label text.
On the dashboard: dot appears before faction/node name in any health widget.

### New: Calculated Value Display (Never Stored)

Effective upkeep and multipliers are always shown as calculated-at-read-time values. The UI must make this clear by showing the formula components alongside the result.

Pattern used on Faction detail and Node detail:

```
EFFECTIVE UPKEEP [section label]
  Base: 80 SP  ×  Overextension: ×1.2  ×  War modifier: +30%  =  112 SP/week
```

- Each component is shown as inline text in 14px/400
- The `=` result is 14px/600/gold (`#c4a45a`)
- PvE faction war modifier shows "N/A (PvE)" in text-muted instead of a percentage
- No edit button on this field — it is purely calculated

### New: Battle Log Entry

Used on War detail page. Reverse-chronological list of battle outcomes.

```
[bg-card card, battle log entry]
  [Date — 11px/400/text-muted, top-right]
  [Node name — 14px/600/text-primary] at [location/node number if available]
  [Attacker faction name] vs [Defender faction name] — [Result badge: Victory/Defeat/Draw]
  [Description — 14px/400/text-muted, italic]
  [Ownership transfer notice if applicable — info alert variant: "Ownership transferred to [Faction]"]
```

### New: Siege Entry

Used on War detail page. Active sieges shown in a dedicated card section above battle log.

```
[ACTIVE SIEGES — section label]
  Each siege:
    [Node being sieged — 14px/600/text-primary] + [Day N of siege — 11px/400/text-muted]
    [Attacker: faction] vs [Defender: faction]
    [Objectives: text — 14px/400/text-muted]
    [Resolve Siege button — ghost variant, small] [Log Battle button — gold variant, small]
```

### New: Diplomacy Agreement Card

Used on Diplomacy list page. Each agreement displayed as a card row.

```
[Alliance/NAP/Trade Agreement badge] [Party A] ↔ [Party B]  [Start date — text-muted]  [End button or Ended badge]
```

## Interaction Contracts

### Inherited from Phase 1 (all apply unchanged)
- `use:enhance` on all forms (no full page reload)
- Inline field validation errors (danger color, 11px/400, below each field)
- Submit buttons: disabled + Loader2 spinner during pending request
- Destructive action always requires a confirmation dialog — never `window.confirm()`
- Confirmation button text repeats the action name (not "Confirm" or "Yes")
- Role-gated elements are omitted from DOM server-side, not hidden via CSS
- Error recovery: danger banner "Something went wrong. Please try again." with form data preserved

### Phase 2 New Interaction Contracts

**Reactive filters (all list pages):**
- Text search: debounced 300ms, client-side filtering via `$derived`
- Select filters: immediate, no debounce
- Filter state is not persisted to URL (no query params needed — admin sessions are short)
- Filter bar is never hidden or collapsible — always visible above the table

**List page row click:**
- Entire table row is clickable (not just a "View" link in actions column), navigates to detail page
- Cursor: pointer on row hover
- Row hover background: `rgba(196,164,90,0.03)` (same as Phase 1 table row hover)
- Actions column buttons (Edit, Delete) do NOT trigger row navigation — use `stopPropagation`

**Edit workflow:**
- Edit opens a modal (not a separate edit page)
- Modal title: "Edit [item name]" (e.g. "Edit Faction", "Edit Node")
- Fields pre-filled with current values
- Save button: "Save Changes" (gold variant)
- Cancel: ghost variant

**Ownership Transfer:**
- Opens a dedicated modal: "Transfer Ownership"
- Fields: New Owner (Select from all factions + "Neutral Territory"), Transfer Method (Select: "Peaceful" / "Violent"), Date (date, default today), Staff Note (textarea, optional)
- Save button: "Transfer Ownership" (gold variant)
- Ownership timeline updates immediately after save (SvelteKit `invalidate`)

**War modifier live update:**
- When a war is declared, war modifier on all involved PvP faction node detail pages updates without a manual refresh (SvelteKit `invalidate` on war creation)
- No toast notification needed — the updated value is visible on the faction/node detail

**Export interaction:**
- "Export JSON" button: triggers a server-side JSON generation and file download immediately — no confirmation dialog
- Download uses browser native download, no new tab

**Import interaction:**
- "Import from JSON" requires file selection first, then shows confirmation dialog
- If no file selected and user clicks "Import from JSON": inline validation error "Please select a JSON file first."
- After confirmed import: full page reload to reflect restored state; success alert "Data imported successfully. Review all sections to verify."

**Pagination:**
- Phase 2 does not implement pagination — VS3 has fewer than 30 factions, ~50 nodes, ~20 wars. All records fit in a single table.
- If record counts grow in season, pagination can be added in Phase 4.

**Source:** UX-02, DATA-06, WAR-01, WAR-02, WAR-06, LOG-01.

## Portal Layout

The portal uses a **simplified shell** — not the full staff shell. The staff shell
(`AppSidebar` + `AppTopbar`) must NOT appear in the portal route group. The portal
shell is portal-specific.

### Portal Shell (`(portal)` route group layout)

```
[Portal Topbar — fixed, h-[48px], bg #231d14, border-bottom #3d3426]
  Left: "VS3 Panel" (15px/600/gold #c4a45a) + separator + faction name (15px/400/text-primary)
  Right: username (14px/400/text-primary) + "Sign Out" button (ghost, 14px/400/text-muted)

[Main content area — pt-[48px], min-h-screen, bg-background]
  [Inner container — max-w-[1100px] mx-auto p-6]
    [Page content rendered here]
```

No sidebar. The portal is a single page (one route: `/portal`). If future phases
add more portal pages, a minimal top-nav tab bar pattern (not a full sidebar) should be used.

**Portal topbar does NOT show role badge.** Member accounts have no role to display.

**Source:** `vs3-panel/src/routes/(portal)/+layout.server.ts` (confirmed portal route group exists,
members collection auth). `vs3-panel/src/routes/(portal)/portal/+page.svelte` (existing stub —
this page is replaced entirely by the Phase 4 implementation).

## Surface Specifications

### Surface 1: Portal Main Page (`/portal`)

Single page. Two logical sections, stacked vertically:
1. My Faction Nodes (PORTAL-01)
2. War & Alliance Board (PORTAL-03)

**No separate routes.** No tab bar needed — the page is compact enough to scroll.
A horizontal rule (`border-border`) separates the two sections.

## Interaction Contracts

### Inherited (all apply unchanged)
All Phase 1–3 interaction contracts apply where relevant. Key ones:
- `use:enhance` on forms (sign-out form)
- Submit buttons: disabled + `Loader2` spinner during pending request
- No destructive actions in portal — no confirmation dialogs needed (PORTAL-04)

### Phase 4 Specific Interaction Contracts

**Portal is fully read-only (PORTAL-04):**
- No form actions other than sign-out exist in the portal route group
- No add, edit, remove, or delete buttons exist anywhere in the portal UI
- No modal dialogs for data entry
- Node cards have no clickable elements beyond the card itself (no detail navigation)
- Server-side: portal load functions use PocketBase `list`/`getOne` only, no `create`/`update`/`delete`

**Data loading — portal page (`/portal`):**
- Single `+page.server.ts` load function fetches:
  1. Faction record for `locals.pb.authStore.record.faction` (the logged-in member's faction)
  2. Nodes owned by that faction (filtered server-side via PocketBase `filter` — never client-side)
  3. All active wars (no faction filter — global)
  4. All active alliances (no faction filter — global)
- All four queries run in parallel: `await Promise.all([...])`
- Effective upkeep per node is computed server-side in the load function using the shared
  `calcUp()` utility from `$lib/upkeep.ts` — same function used in staff panel (UPKEEP-02)
- Upkeep status (paid/partial/underfunded/unpaid) computed server-side from cycle SP totals

**Faction privacy (PORTAL-02):**
- Node query uses PocketBase collection rule: `@request.auth.faction = faction`
  This is enforced at the database level; the UI does not need additional filtering.
- Portal load function passes `locals.pb` (member-scoped auth) — never an admin client.
- No client-side filtering or hiding; if a query somehow returns another faction's data,
  that is a PocketBase rule misconfiguration (caught by Phase 1 integration test).

**Sign-out:**
- Same `use:enhance` form POST to `/login?/logout` as staff panel topbar
- On success: redirect to `/login`
- Button shows `Loader2` spinner while pending (same pattern as AppTopbar.svelte)

**Error states:**
- If the member's faction record is not found: show full-page error card
  (bg-card, border-border, centered) with message "Your faction could not be found.
  Please contact a staff member." — no retry button.
- If a network/PocketBase error occurs during load: SvelteKit's `error()` helper returns
  a 500 page — the existing `+error.svelte` (if present) handles display.
- Session expiry: `+layout.server.ts` redirect to `/login?expired=true` (already implemented).

**No pagination on portal:**
- Faction nodes: a single faction is unlikely to own more than 20 nodes. No pagination needed.
- Wars list: global active wars rarely exceed 10 entries. No pagination needed.
- Alliances list: global active alliances rarely exceed 10 entries. No pagination needed.
- If any list exceeds 50 entries, a muted count line is shown below:
  "[N] items shown" (11px/400/text-muted) — no "load more" control.

**No real-time updates:**
- Portal uses standard SvelteKit load (no SSE / PocketBase realtime subscription)
- Members are expected to refresh the page to see latest cycle data
- No "last updated" timestamp shown — portal is a reference view, not a live dashboard

**Source:** PORTAL-01, PORTAL-02, PORTAL-03, PORTAL-04. CLAUDE.md (faction privacy at query level,
calcUp shared function). Phase 1 auth architecture.
